# M3 검토: 텍스처 아틀라스 여러 장 자동 분할

명세 2.3 / 16장 M3의 "다중 아틀라스 분할 검토" 결과. **v1에서는 자동 분할을 하지 않고, 필요 여부를 판단하는 용량 검사만 넣었다.**

## 구현한 것: 용량 검사 (`core/uvmath.atlas_capacity`, `bl/collect.capacity_check`)
- 소스가 실제로 쓰는 텍셀 = Σ(머티리얼의 가장 큰 이미지 해상도² × 그 머티리얼 면의 소스 UV 면적). 타일링도 면적에 그대로 포함된다.
- 아틀라스 용량 = W × H × 0.7(패킹 사용률 가정, 실측 0.44~0.70).
- 비율이 1.05를 넘으면 검사에서 경고를 낸다: "아틀라스가 N배 커야 함, 선명도 약 X%로 감소, 권장 해상도 / 분할 장수".
- 테스트: 단위 `test_capacity`, 통합 `M3_capacity_warning` (2048² 텍스처 3장 → 512 아틀라스는 경고, 8192는 통과).

## 자동 분할을 미룬 이유
1. **드로우 콜 목표와 충돌.** 명세 2.1의 목적은 "드로우 콜 1개"다. 분할하면 머티리얼이 N개가 되고, 오브젝트가 아틀라스 경계를 넘지 않게 나눠야 해서 Join 결과도 N개가 된다.
2. **나누는 기준은 프로젝트마다 다르다.** 오브젝트별, 머티리얼별, 화면 크기(LOD 그룹)별, 텍셀 밀도별 중 무엇으로 나눌지는 아트 디렉션에 달려 있어서 자동 기본값을 정하기 어렵다.
3. **대안이 이미 있다.** 해상도를 8192까지 올리거나, FR-26 가중치로 중요한 오브젝트에 해상도를 더 주거나, 오브젝트를 나눠 선택하고 이름을 달리해 두 번 실행하면 된다(예: `Props_A`, `Props_B`).

## 구현하게 되면 (제안)
- 단위: **오브젝트**. 한 오브젝트의 면은 한 아틀라스에만 들어간다. 머티리얼 단위로 나누면 한 메시가 두 머티리얼을 쓰게 돼 드로우 콜 이득이 사라진다.
- 알고리즘: 오브젝트별 필요 텍셀(위 식)을 구한 뒤 First-Fit Decreasing으로 `W×H×0.7` 크기의 통(bin)에 담는다. `core/`에서 순수 함수로 테스트할 수 있다.
- 실행: 통마다 지금의 파이프라인을 `<이름>_0`, `<이름>_1` … 으로 돌린다(`Pipeline`을 재사용하므로 롤백과 매니페스트 구조는 그대로). 매니페스트 최상위에 `"sheets": [...]`를 추가한다(schema 2).
- UI: 채널 섹션 아래 `분할: 끔 / 자동(최대 N장)`.
- 예상 작업량: core 함수와 테스트 0.5일, 파이프라인 반복과 UI 0.5일, 통합 테스트 0.5일.
